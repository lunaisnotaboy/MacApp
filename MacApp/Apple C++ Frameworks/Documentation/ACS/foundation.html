Foundation

ACS provides low-level APIs that are modeled on the Macintosh toolbox APIs, and high-level APIs that are modeled on the C++ Standard Library.

ACS has wrapper classes for almost all of Core Foundation types.

The Foundation classes are designed to provide full access to the Core Foundation APIs. For each Core Foundation function, there is a corresponding method in the appropriate Foundation wrapper class. The methods are scoped by their class, so they can have shorter names than the Core Foundation functions. For example, data->GetLength() will do the same thing as CFDataGetLength(data). The only difference is that if 'data' is NULL, the C++ method will throw a logic_error exception, because the Core Foundation functions should never be called for a NULL object. Similarly, if a Core Foundation Create function returns NULL instead of successfully allocating an object, the C++ wrapper will throw a bad_alloc exception.

Each wrapper class has an operator that provides automatic conversion to its corresponding Core Foundation type reference. For example, CCFData has an operator CFDataRef. This makes it easy to convert incrementally to the C++ interfaces, and to use C libraries from C++ programs.

CCFObject

CCFObject wraps a CFTypeRef, which is a reference to a generic object in Core Foundation. Most of the Foundation classes are subclasses of CCFObject.

CCFRange

CCFRange is a subclass of the Core Foundation CFRange structure. It provides an inline constructor that can be used instead of the CFRangeMake macro.

DynamicCast

DynamicCast is a templatized function for safely casting a CFTypeRef to another Core Foundation reference type, such as CFStringRef. The generic version of DynamicCast is not defined on purpose, so you will get a link error if a necessary specialized version of DynamicCast is missing. The specialized versions of DynamicCast call the helper template function DynamicCastID, passing in the CFTypeID for the desired type. If the pointer has the right ID, the cast goes through, otherwise DynamicCastID returns NULL.

Please note that in Core Foundation, an object has only one type ID, and the type IDs are not in a hierarchy (except that every type is also a CFTypeRef). This means that multiple classes in ACS may map onto the same CF type ID. For example, CCFXMLTree is a CCFTree.

Retain and Release

Retain and Release are templatized convenience functions that make sure the provided pointer is not NULL before calling CFRetain or CFRelease, respectively. Because they are global functions, they can be used in static methods and constructor mem-initializers without having to first turn the pointer into a CCFObject. Also, the Retain template function returns the pointer with its actual type instead of casting it to a CFTypeRef.

TemplateAuto

TemplateAuto implements an automatically reference counting pointer based on a type T. T must must be a smart pointer class that defines these types and functions:

  pointer
  T(pointer)
  pointer get() const
  set(pointer)
  reset(pointer)

The constructor and the set function should just do simple assignment. The reset function should release the old pointer and retain the new one before making the assignment.

TemplateAuto assumes that the pointed to objects are created with a retain count of one. Therefore, assignment from an ordinary pointer doesn't do another retain, because the destructor should fully release the object. Assignment from another auto-pointer does do a retain. This will do the right thing, as long as you don't try to fool the auto-pointer into thinking it is getting an ordinary pointer. For example:

  autoptr1 = ptr; okay; takes over ownership
  autoptr1 = autoptr2; okay; does a retain
  autoptr1 = autoptr2.get(); not okay

Specialized Object Types

Most of the Foundation classes have the same general design. For specific details, see the individual class headers.

Taking CCFData as an example, CCFData wraps a CFDataRef. CCFData is a subclass of CCFObject, which already has a CFTypeRef fReference data member. Rather than define its own reference, CCFData provides its own get, detach, set and reset functions so the reference can be accessed as a CFDataRef. Along with CCFData is a specialization of DynamicCast<CFDataRef>(CFTypeRef ptr). CCFData can be constructed from a CFTypeRef; the constructor uses DynamicCast so the resulting object will be NULL unless the passed in pointer has the right ID. For convenience, there are some other constructors that call through to the equivalent Create functions. The constructors don't have the initial allocator parameter, because most programs should pass in a NULL allocator except in special cases. The Create functions are static member functions. Some CF object types so many Create functions, it isn't possible to provide convenience constructors for all of them without ambiguity. CCFData is relatively simple so all of its Create functions are covered.

CAutoCFData uses TemplateAuto to make a version of CCFData that automatically cleans up after itself. It's a subclass of TemplateAuto<CCFData> rather than a simple typedef, because the template can't replicate all the convenience constructors.

CCFMutableData wraps a CFMutableDataRef. In Core Foundation, CFDataRef is a const pointer to an internal __CFData structure, and CFMutableDataRef is an ordinary non-const pointer to the same structure. CCFMutableData is defined as a subclass of CCFData so it inherits all the const methods, and just adds the methods that can change the data. This reflects the underlying design of the Core Foundation data objects. This design makes sense if you think of CCFMutableData as the normal object that may or may not be changed, and CCFData as an optimized reference for constant data only.

CAutoCFMutableData is the auto-pointer version of CCFMutableData.
