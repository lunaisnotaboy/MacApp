Network Design

Utilities

Open Transport provides C++ versions of its interfaces. These APIs are very nice, but there is a limit as to how far they can go in supporting C++ because the same headers still need to be usable for C clients. Network extends some of the Open Transport classes by adding constructors, conversion operators, and convenience functions. The extensions are intended to make the Open Transport classes safer and more convenient to use in a modern C++ environment, without changing their behavior.

COpenTransport

COpenTransport has static member functions that wrap the APIs for checking if Open Transport is present, if TCP/IP support is available, and for opening and closing Open Transport.

The class uses the singleton pattern so there may be at most one COpenTransport object instance in the application. The instance keeps a reference count of the number of other objects that are using Open Transport. When the COpenTransport instance is created it initializes Open Transport. When the reference count falls to zero, the instance is deleted and it closes Open Transport. The instance is private to the class because clients can do everything they need using the Initialize and Terminate static member functions.

MUsingOpenTransport

MUsingOpenTransport holds Open Transport open for the life of the object. Its constructor calls COpenTransport:: Initialize, and its destructor calls COpenTransport:: Terminate.

Classes that need to initialize and terminate OpenTransport, such as CTCPEndpoint, can do so simply by mixing in MUsingOpenTransport.

CUsingOpenTransport

CUsingOpenTransport is a stack based object that works around a problem with the C++ compiler not generating code for constructors of objects that have no data.

CUsingOpenTransport is intended for use in procedural code that needs to initialize and terminate Open Transport.

ThrowIfOSStatus

The Open Transport APIs return a 32-bit OSStatus. Network provides a ThrowIfOSStatus global function that is similar to ThrowIfOSErr_AC. Internally ThrowIfOSStatus calls ThrowError_AC which cuts the error status down to 16 bits. This is not optimal, but it is something that can be fixed in the future. It is important for all code that has an OSStatus result to call ThrowIfOSStatus and not ThrowIfOSErr_AC.

CInternetServices

In order to make DNR calls, Open Transport requires opening internet services. CInternetServices has static member functions that open internet services, if it isn't already open, and then make the corresponding DNR call.

CInternetServices will throw an exception if it can't open internet services at all. For everything else it returns the status. If the DNR successfully determines that an address doesn't exist, that doesn't mean that the program has failed. It should be up to the caller to decide whether to throw an exception because of a DNR error status.

The internet services require Open Transport to be initialized, so CInternetServices mixes in MUsingOpenTransport.

CInetAddress

CInetAddress wraps an Open Transport InetAddress structure. InetAddress is essentially an OTAddress with an fAddressType that must always be AF_INET. The rest of the structure contains a 32-bit IPv4 InetHost number, such as 127.0.0.0, and a 16-bit port number.

The CInetAddress constructors ensure that the address type is always AF_INET. They also allow constructing the address from a host name, such as "www.apple.com", as well as an InetHost number or another CInetAddress. Please note that converting an address from a host name to a number involves a lookup which may take a while, and could time out or fail.

CInetAddress provides functions for converting itself to a dotted string, such as "127.0.0.0". The ToDottedString method sets a provided C string. The AsString method returns a C++ string.

There is an output stream operator for CInetAddress which outputs the port number as well as the dotted string, as in "127.0.0.0:123". As a convenience, there is an output stream operator for InetAddress that casts the address to a CInetAddress for you.

Because InetAddress is specific to IPv4, developers should avoid using CInetAddress and InetAddress except where absolutely necessary. Host names will be fully compatible with IPv6. Besides, names are more user-friendly than numbers.

CDNSAddress

CDNSAddress wraps an Open Transport DNSAddress structure. DNSAddress is essentially an OTAddress with an fAddressType that must always be AF_DNS. The rest of the structure contains a 256 character C string. (The 255 character maximum length is adequate because it's just for a host name, not for a URL. Even long host names such as "www.natural-guard.department-of-redundancy-department.gov" fit easily with 255 characters.)

The CDNSAddress constructors ensure that the address type is always AF_DNS. They allow constructing the address from a host name or another CDNSAddress.

There is no constructor for making a CDNSAddress from an InetHost number. If all you have is a host number, either make a CInetAddress or call CInternetServices:: AddressToName to do a reverse lookup.

CDNSAddress has assignment operators that copy the name from a C string or another DNSAddress.

CDNSAddress provides an AsString method that returns a copy of the host name in a C++ string.

There are output stream operators for CDNSAddress and DNSAddress that write the host name string to the stream.

CNetbuf

CNetbuf wraps an Open Transport buffer reference. It is bitwise compatible with TNetbuf because it doesn't have any virtual functions.

TemplateNetbuf

TemplateNetbuf is a templatized function that returns a CNetbuf. It uses the type from the template to fill in the structure size.

There is a specialized version of TemplateNetbuf for DNSAddress, that computes the actual length based on the length of the address name, the way Open Transport expects it.

TemplateNetbuf can be specialized for other structure types simply by providing another version of the function. Use TemplateNetbuf(DNSAddress&) for an example.

TemplateNetbuf is used by CCall.

CCall

CCall wraps an Open Transport connection call structure. A TCall has a TNetbuf for the address to connect to. CCall has constructors so the address can be an InetAddress or a DNSAddress. In each case, it uses TemplateNetbuf to set up the reference to the address.

CCall doesn't do anything with the options and user data fields except clear them.

The address referred to by the CCall is not copied. It needs to stay around for the life of the CCall.

CEndpointInfo

CEndpointInfo wraps an Open Transport TEndpointInfo structure. CEndpointInfo adds a Clear method and the ability to construct itself from a TEndpoint.

MSyncIdler

MSyncIdler has an Open Transport provider notifier callback. When it gets a sync idle event it calls HandleSyncIdleEvent. The endpoint classes mix in MSyncIdler and override HandleSyncIdleEvent to work with their idler.

MProviderNotifier

MProviderNotifier is a subclass of MSyncIdler that has a virtual function for each kind of OT event that may come in. It is not used in Network.

CReceived

CReceived is designed so that a receive function can return the length of data received and the associated OTFlags in one object. Most code is interested only in the length, so there is an operator long() that provides access to the length. operator=(long) sets the length. The bitwise operators (~, |, &, ^) access the flags, as do the Set and Clear methods.

Please note that the length is not an OTResult. If there is no way any more data will be received on a connection, the receive function will return -1, not kOTLookErr. A kOTNoDataErr should be handled by returning 0. All other errors will be thrown as an exception.

TCP/IP

CIPEndpoint

CIPEndpoint provides a common base class for CRawIPEndpoint and CTCPEndpoint.

CIPEndpoint mixes in MSyncIdler so it can support sync idle events. It mixes in MUsingOpenTransport so Open Transport will be initialized and kept open as long as it is around. It mixes in MConnectionTraceComposite so it can support progress reporting and debug logging.

CIPEndpoint knows how to open the endpoint, bind it to an address, unbind it, and close it. It knows how to get the endpoint status. It can get and set endpoint options.

The sync idle handler works with a CYielder_AC object so it yields at a controllable rate. The sync idle handler also supports canceling synchronous calls. This allows pending I/O to be aborted when the endpoint must go away. This feature should be used only when absolutely necessary because Open Transport leaves the endpoint in a bad state and the only safe thing to do after canceling an endpoint is to delete it.

CRawIPEndpoint

CRawIPEndpoint is an IP endpoint that can send and receive raw IP datagrams.

The Open method is overridden so the default configuration is RawIP.

The Send method sends a datagram to an address.

GetSendError receives the error status from a failed send.

The Receive method receives a datagram from an address. Receive takes a timeout which defaults to kForever. Receive does not wait until the buffer is full. As soon as data is available or the timeout expires, it will return however much data it has received.

The Available method returns the amount of data that is currently available for reading. It is a minimum, not an exact count, because more data may arrive at any time.

CTCPEndpoint

CTCPEndpoint is an IP endpoint that supports connection oriented TCP/IP communications.

The Open method is overridden so the default configuration is TCP/IP.

The Connect method connects to an IP or DNS address. The Disconnect method is used to perform an orderly disconnect (initiated from this end). The HandleLook method is used to handle kOTLookErr results, which usually happen when the endpoint is being disconnected from the other end.

The constructor is overloaded so an endpoint can be opened and connected to an address all at once.

The Send method sends data to the other end.

The Receive method receives data from the other end. Receive takes a timeout which defaults to kForever. Receive does not wait until the buffer is full. As soon as data is available or the timeout expires, it will return however much data it has received. It will return -1 if the endpoint has been disconnected.

The Available method returns the amount of data that is currently available for reading. It is a minimum, not an exact count, because more data may arrive at any time. It will return -1 if the endpoint has been disconnected.

CTCPCharIO

CTCPCharIO is a CTCPEndpoint that is used for character and line oriented communications.

CTCPCharIO provides methods that are similar to the C++ Standard Library iostreams.

MConnectionTrace

MConnectionTrace provides hooks for monitoring connection progress and for debug tracing. It is an abstract protocol, all the method implementations are empty. The APIs are designed around CTCPEndpoint. They really aren't intended for use with anything else.

You can use multiple MConnectionTrace objects with the same connection, by grouping them under a MConnectionTraceComposite. If a MConnectionTrace object can automatically add itself to a composite when it is constructed and will remove itself when it goes away. The SetParent method makes sure the trace object has only one parent.

Developers who want to do custom tracing or progress monitoring probably should subclass from MConnectionTrace.

MConnectionTraceComposite

MConnectionTraceComposite keeps a list of MConnectionTrace references and calls them whenever it is called. The composite does not own the referenced objects.

MConnectionTraceComposite has a SetInhibit method that can be used to inhibit passing on calls to its contained objects.

InhibitTracing

Temporarily inhibits or enables tracing. Useful for functions that can do a better job of tracing than the lower level methods they call.

Buffers

CMemBlock and CAutoMemBlock

CMemBlock manages a block of characters in the MacApp memory heap. CAutoMemBlock is a CMemBlock that automatically deletes its block in its destructor.

CMemBlock is designed to be a lightweight class for efficiently managing data that is being sent or received across the internet. It is essentially a smart char* pointer that knows how to allocate its storage from the MacApp memory heap, resize its storage, and delete its storage. CMemBlock doesn't have any virtual functions so its size is the same as a char*.

CAutoMemBlock is the auto-pointer version of CMemBlock.

CTextBuffer

CTextBuffer was originally based on a smart buffer class from CyberDog. It has been rewritten for modern C++ and MacApp.

The easiest and safest way to access the contents of a CTextBuffer is through a CTextPtr.

CTextBuffer makes it easy for an application to process data as it comes in. The AssureData method makes sure the buffer has data at a requested offset. Subclasses of CTextBuffer can override AssureData to get more data when it is needed. For example, CThreadedTextBuffer waits for data to be provided by another thread.

To do:
Consider a sparse buffer organization. Right now, CTextBuffer has a single memory block for its contents. Growing the buffer requires copying to a new larger block. Allocating a very large block may not be possible. Going to a sparse organization would allow the buffer to grow without copying or moving the old storage. It could also allow least recently used blocks to be purged to a disk cache.

CThreadedTextBuffer

CThreadedTextBuffer is a CTextBuffer for use when one thread is putting data into the buffer and another thread is processing it. While the buffer doesn't have the needed data, the AssureData method calls CAbstractThreadContext_AC:: YieldCurrentContext, which translates into a call to YieldToAnyThread. Eventually one of the other threads will do one of the following operations:

  • Provide the needed data. When AssureData regains control it will return true.
  • Set the buffer status to complete. There is no error, but AssureData will return false because it has reached the end of the data.
  • Set the buffer status to aborted. AssureData will return false because it has reached the end of the data.

ThrowIfNullTextPtr

If the provided pointer is NULL, ThrowIfNULLTextPtr throws a minErr ("unable to ... because of a program error."

This function is necessary because ThrowIfNULL_AC throws a memFullErr ("out of memory") and ThrowNonObject_AC will throw on odd addresses as well as NULL.

To do:
Consider defining a more specific error to throw.

CConstTextPtr

CConstTextPtr provides access to a const CTextBuffer. Because of the way C++ works, a const CTextPtr is an unchangeable pointer into a changeable buffer. We want a changeable pointer so we can access different characters in the buffer, while guaranteeing that the buffer won't be changed.

CTextPtr

CTextPtr is a pointer into a CTextBuffer. In order to save on code size, it's implemented as a subclass of CConstTextPtr with const_cast statements added where necessary.

CTextPtr comes with a small number of utility functions similar to the Standard C Library string functions. This allows a CTextPtr to be used as if it were a char*.

Threads

TCommandThread

TCommandThread maintains a queue of threaded commands, and runs each command within its context. TCommandThread is designed to be the base class for a threaded command handler. Override the DoInitialState and Terminate methods if you need to do set up and clean up within the thread. Post threaded commands to do work in the thread.

TThreadedCommand

TThreadedCommand is a command that can do a task in a thread. When it is done as a thread, it becomes ready to execute as a command. To use a threaded command, override the Run method to do work in a thread. Override the DoIt method to do any work you need done after the thread is complete. When you create an instance of your threaded command, post it to the application's command list, then run the thread part of the command. TThreadedCommand is designed to be used with TCommandThread, but it should be possible to run it in its own thread using code similar to the code in RunCommand.

TThreadCommand

TThreadCommand is a command that reports any errors from a thread and releases the thread. TThreadCommand is intended to be a simpler solution that can replace TThreadExceptionHandler and TThreadExceptionCommand in UThreads.

To use TThreadCommand, create one with a reference to a thread, post the command, and start the thread. If you want to do custom post-processing, make a subclass and override DoIt.

TThreadIdler

TThreadIdler is a simple co-handler that calls YieldToAnyThread. It ensures that cooperative threads get time.

Debugging

CConnectionLog

CConnectionLog is a MConnectionTrace that is used for debug tracing of the connection. In debug builds of an application, calls to the connection log are printed to the log window.

Sent data and received data are shown in different colors. Data containing non-printing characters is dumped as ASCII codes.

PrintSink

PrintSink defines a print function that can print to a CCharOutputSink_AC, such as dout. For examples of how it is used, see CConnectionTrace and CPingProtocol.

TLogWindow

TLogWindow maintains the debug log window that is used in the MacApp-based Network example applications.

TWEViewStream

TWEViewStream is a CCharOutputSink_AC that feeds into a TWEView. Because it uses WASTE, it can handle >32K of text, although it does tend to slow down when the line count goes up.

Protocols

Ping

CPingProtocol owns a CRawIPEndpoint and does the pinging.

TPingClient is a CCooperativeThread_AC that owns a CPingProtocol.

Consider merging TPingClient and CPingProtocol.

Simple Terminal

CTerminalProtocol owns a CTCPEndpoint and knows how to transmit and receive data over a TCP/IP connection. There is some preliminary implementation for Telnet, but it is not hooked up yet. It works fine for other protocols if you don't connect to the Telnet port.

TTerminalClient is a TCommandThread that owns a CTerminalProtocol. It overrides TCommandThread's Run method because it needs to check for received data before sending anything. The TTerminalClient has a pointer to a TEventHandler that will get any received data, and a command number that it uses to notify the event handler that data has been received. The data is actually conveyed using a TTerminalReceiveCommand so there aren't any threading issues.

TTerminalCommand is a base class for working with TTerminalClient.

TTerminalConnectCommand asks the protocol to connect to an IP address and port.

TTerminalSendCommand asks the protocol to transmit some data over the connection.

TTerminalReceiveCommand is a simple TCommand that holds some received data and delivers it to the TEventHandler that wants it.

Server

CListenerThread implements a generic listener. It sits on an IP address and port, and listens for a connection request to come in. It makes a server thread to handle the connection. You need to override DoMakeServerThread for your protocol. You can override WillAccept to look at requests and decide whether to accept them.

CServerThread provides the framework for handling a connection from a client. If you want to use a subclass of CTCPEndpoint with the server, you may override DoMakeEndpoint. You need to override ReceiveRequest to receive a request from the client, and SendResponse to process the request and send the response. When the conversation is done, return false from either ReceiveRequest or SendResponse, and the server thread will disconnect from the client and go away.
