Building with Project Builder

MacApp comes with support for building with Project Builder on Mac OS X 1.0. All of the necessary projects are in the 'PB Support' folder. The layout of the 'PB Support' folder matches the layout of the Apple C++ Frameworks sources.

Building the Libraries

MacApp.pbproj builds MacApp as a static library. It has multiple targets for building the debug and non-debug versions of the library.

The 'MacApp library' target builds the non-debug version of the MacApp static library. The result is a file 'libMacApp.a' in the 'build' folder next to the project. In order to make it easier for application projects to get to the MacApp headers, the headers are copied to an 'includes' folder, also next to the project. Because of a bug in Project Builder, the build process leaves intermediate files for the headers in the project folder. Please ignore them and do not use them.

The 'MacApp debug library' target builds a static library file 'libMacApp_d.a' in the 'build' folder next to the project. It is just like lib_MacApp.a, except it is built with qDebug turned on, debugging symbols, and no optimization. This target will also set up the 'includes' folder and leave intermediate header files in the project folder.

The project does not include all of the ACS suites. The Memory suite is not included because applications should use Mac OS X memory allocation instead. TidyHeap is not included because applications should use Mac OS X MallocDebug. The FTLString class is not included because it will not compile with the version of STL on Mac OS X.

Building Your Own Application

The best approach seems to be to reference the MacApp static library where it is built. This means using paths relative to the application project, or using absolute paths that are necessarily machine specific, so the easiest way to set up an application project is to start from scratch.

In Project Builder, create a new project using the 'Carbon Application' stationery or whatever other stationery is appropriate. Create all the targets, such as debug and final, before you add any files. For the debug target, drag in 'libMacApp_d.a' from the MALibraries build folder, and 'MacAppPrefix_d.h' from the MALibraries includes folder. Similarly drag in 'libMacApp.a' and 'MacAppPrefix_n.h' for the final target. In the build settings panel for each target, add Header paths to /Developer/Headers/FlatCarbon/, and to the MALibraries includes folder (use get info on the MacAppPrefix file to get the path). In the expert settings, for the COPTIONS setting, add a -include and the path to the MacAppPrefix file.

Debugging is easy, because GDB knows where the MacApp sources are. All you need to do is open the MacApp.pbproj so you can set breakpoints in MacApp code.

Notes

The ResMerge phase will not replace existing resources in an application even though they have changed. New resources will be added. Should you change a resource and need to rebuild you will need to 'Clean' your project prior to rebuilding.

Project Builder recognizes when a source file has been modified outside of Project Builder so it is fine to use some other source editor if desired.

Known Problems

Be careful about selecting a library file, such as 'libMacApp_d.a', in Project Builder. If you click directly on it in the files list, Project Builder will try to display its contents as text. Library files are big, so this may take a really long time. To avoid that, if you need to select a library file, click on something else and use the arrow keys to get to it.

During the build, you will get several compiler warnings about "Choosing ... over ... const because it has a better conversion sequence." These warnings can be ignored. When template code is involved, there will be a warning "Instantiated from here", that Project Builder will misinterpret as an error. These errors can be ignored.

File-mapped resources may be odd-aligned when built with Project Builder. Various changes have been made in MacApp to accomodate this. You may need to change your code if you word-align offsets for sub components of resources.

We are not using pre-compiled headers at this time.
