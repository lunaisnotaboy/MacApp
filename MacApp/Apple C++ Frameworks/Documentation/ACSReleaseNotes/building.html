Building ACS Release XV.I

Project Builder

ACS comes with support for building with Project Builder on Mac OS X 1.0. All of the necessary projects are in the 'PB Support' folder. Inside the 'PB Support' folder is an ACS folder, which is where all the ACS projects live. Inside that, the ACSLibraries folder contains the ACS libraries build project, ACS.pbproj. The layout of the 'PB Support' folder matches the layout of the ACS sources.

ACS.pbproj has multiple targets, for building ACS as a framework and as a static library, and debug and non-debug versions of each. Whether you build ACS as a framework or as a static library is up to you. It is much easier to create a project for an application that uses an ACS framework. Applications that use a framework are smaller. Projects that use the ACS static library are easier to debug, and there is no need to worry about framework version control. The ACS examples use the ACS frameworks, so if you are going to build the examples, you should build the frameworks first.

ACS.pbproj does not include all of the ACS suites. The Memory suite is not included because applications should use Mac OS X memory allocation instead. TidyHeap is not included because applications should use Mac OS X MallocDebug. The FTLString class is not included because it will not compile with the version of STL on Mac OS X.

Building the ACS Frameworks

The 'ACS framework' target builds a folder called ACS.framework, that contains a copy of the ACS headers, and an ACS shared library. At the end of the build, ACS.framework is copied to /Library/Frameworks/ on your local Mac OS X system disk.

The 'ACS debug framework' target builds a folder called ACSDebug.framework. It is just like ACS.framework, except it is built with qDebug turned on, debugging symbols, and no optimization. At the end of the build, ACSDebug.framework is copied to /Library/Frameworks/ on your local Mac OS X system disk.

The 'ACS frameworks' target builds both the ACS framework and the ACS debug framework.

Building the ACS Examples

The example projects are in the 'Examples' folder next to the 'ACSLibraries' folder. All the of the example projects provided build and run correctly.

Building Your Own Application

Before you create your own application project, copy the 'ACS Tool' stationery into the Project Builder Extras folder. Copy the entire 'ACS Tool' folder, not just the Project Builder Project. It should go in /Developer/ProjectBuilder Extras/Project Templates/Tool/.

Open Project Builder, choose 'New Project', and choose 'ACS Tool' from the list of project stationery. Specify the name of the project and where you want it to go. If you want the project to be in its own folder, make sure the new folder is in the project path.

Replace 'main.c' with your own source code files. When adding files, Project Builder will display a sheet dialog where you can tell it which targets to add the files to. If the sheet is too small you may not be able to see the list of targets, but you can resize it just like a window. Make sure both the debug and final targets are selected.

At this point, you are ready to build. Because the project references the ACS frameworks that have been copied to /Library/Frameworks/, it does not matter where the project is located. Of course, you may need to fix compile errors, or add system frameworks to the project to resolve undefined link references.

When you are debugging your application, if you have the ACS.pbproj open as well as your application project, you can set breakpoints in ACS code. Stepping down into the ACS framework is also possible, but it takes some extra work to set it up. Use the 'directory' command in the Console pane to tell GDB the absolute paths to the folders containing the sources you want to see. You can get the absolute path by selecting a file or folder in the file list in ACS.pbproj, doing a 'Get Info' (command-i), selecting the absolute path text in the info window and copying it.

Building the ACS Static Libraries

The 'ACS library' target builds the non-debug version of the ACS static library. The result is a file 'libACS.a' in the 'build' folder next to the project. In order to make it easier for application projects to get to the ACS headers, the headers are copied to an 'includes' folder, also next to the project. Because of a bug in Project Builder, the build process leaves intermediate files for the headers in the project folder. Please ignore them and do not use them.

The 'ACS debug library' target builds a static library file 'libACS_d.a' in the 'build' folder next to the project. It is just like lib_ACS.a, except it is built with qDebug turned on, debugging symbols, and no optimization. This target will also set up the 'includes' folder and leave intermediate header files in the project folder.

Building an Application Using the Static Libraries

If you wish to use ACS as a static library, the best approach seems to be to reference the library where it is built. This means using paths relative to the application project, or using absolute paths that are necessarily machine specific, so the easiest way to set up an application project is to start from scratch.

In Project Builder, create a new project using the 'Carbon Application' stationery or whatever other stationery is appropriate. Create all the targets, such as debug and final, before you add any files. For the debug target, drag in 'libACS_d.a' from the ACSLibraries build folder, and 'ACSPrefix_d.h' from the ACSLibraries includes folder. Similarly drag in 'libACS.a' and 'ACSPrefix_n.h' for the final target. In the build settings panel for each target, add Header paths to /Developer/Headers/FlatCarbon/, and to the ACSLibraries includes folder (use get info on the ACSPrefix file to get the path). In the expert settings, for the COPTIONS setting, add a -include and the path to the ACSPrefix file.

Debugging with the static library is easy, because GDB knows where the ACS sources are. All you need to do is open the ACS.pbproj so you can set breakpoints in ACS code.

Known Problems

Be careful about selecting a library file, such as 'libACS_d.a', in Project Builder. If you click directly on it in the files list, Project Builder will try to display its contents as text. Library files are big, so this may take a really long time. To avoid that, if you need to select a library file, click on something else and use the arrow keys to get to it.

During the build, you will get several compiler warnings about "Choosing ... over ... const because it has a better conversion sequence." These warnings can be ignored. When template code is involved, there will be a warning "Instantiated from here", that Project Builder will misinterpret as an error. These errors can be ignored.

Indexing ACS.pbproj may cause Project Builder to crash.

We are not using pre-compiled headers at this time.

File-mapped resources may be odd-aligned when built with Project Builder. Various changes have been made in ACS to accomodate this. You may need to change your code if you word-align offsets for sub components of resources. The alternative is to go into the Applications Settings panel of the Project Settings window, click on Expert, and remove the flag entry 'CSResourcesFileMapped'. This will prevent resources from being file-mapped.

CodeWarrior

ACS comes with projects for building with CodeWarrior Pro 6 and CodeWarrior Pro 7, on Mac OS X and Mac OS 8 and 9.

CodeWarrior Pro 6 Support

ACS supports building with CodeWarrior Pro 6. The recommended configuration is CodeWarrior Pro 6.2.

CodeWarrior Pro 6 comes with a modified version of the CarbonLib 1.0.4 SDK. For Carbon development, we strongly recommend installing the CarbonLib 1.4 GM SDK, which is freely downloadable from the Apple Developer web site. The CarbonLib SDK contains the latest versions of the headers, so it is preferred for non-Carbon development too.

All of the necessary projects are in the 'CWP6 Support' folder. Inside the 'CWP6 Support' folder is an ACS folder, which is where all the ACS projects live. Inside that, the ACSLibraries folder contains the ACS libraries build projects. The layout of the 'CWP6 Support' folder matches the layout of the ACS sources.

There are three CodeWarrior projects in the ACSLibraries folder. ACSLib.prj is for building ACS for Classic 68K and PPC. ACSLib_car.prj is for building ACS for Carbon. ACSLib_win.mcp is for building ACS for Windows.

To build ACSLib, open the project for the platform you want to build for, choose 'All Mac OS Targets' or 'All Carbon Targets' as the target, and choose 'Make' or 'Bring up to date'.

CodeWarrior Pro 7 Support

All of the necessary projects are in the 'CWP7 Support' folder. The layout of the 'CWP7 Support' folder is the same as 'CWP6 Support', except that CodeWarrior Pro 7 does not support development for 68K. Use CodeWarrior Pro 6 for building 68K applications.

CodeWarrior Pro 7 has greatly improved support for Mach-O development, but the ACS projects are not quite ready yet, so they are not included. Use Project Builder for Mach-O development.

Building the ACS Examples

The example projects are in the 'Examples' folder next to the 'ACSLibraries' folder. All the of the example projects provided build and run correctly.

There are aggregate projects that will build all the ACS examples. ACSExamples.prj builds all the examples for Classic 68K and PPC. ACSExamples_car.prj builds all the ACS Carbon examples. Please note that several of the examples are Carbon specific and do not have Classic projects. One of the examples, TESample, is not carbonized at this time and so has only a Classic project. Finally, the Counter example takes a little longer to build so it is left to be built separately.

Building Your Own Application

Drag the ACS library project you want to use into your application project, and drag in the built ACS libraries. Make sure the target settings in your application project match the corresponding settings in the ACS library project, especially the C/C++ language, processor, and optimization settings.

For Classic PPC debug applications, drag in TidyHeapSharedLib from inside the TidyHeap/SharedLib folder. TidyHeap will work without the shared library, so it can and probably should be weak linked. TidyHeap does require a CreateTidyHeap factory function. The factory function was left out of the ACS library on purpose so it would be easier for applications to specify their own. You can include DefaultCreateTidyHeap_AC.cpp or MinCreateTidyHeap_AC.cpp in your project, or use them as examples for creating your own custom tidy heap.

If you want to use only some parts of ACS, or build ACS with a different options, it may be easier to include the ACS sources directly into your application project. Please note that you don't want all the files in the ACS Suites folder tree. Drag the files you want from an ACS library project, not the Finder.

Known Problems

Due to the early state of the Metrowerks Mach-O tools, there is no ACSLib_macho.prj; use Project Builder to build ACS for Mach-O.

MPW

MPW support is not provided in this release. The Apple C++ Frameworks team has been working on simplifying and improving the MPW support, but enough other issues remain that it isn't possible to provide working MPW support at this time, even on an experimental basis.

The last working version of MPW support was contributed by the heroic Yoshida-san for MacApp R13u4.1. It can be found at the MacApp developer contributions page.

STLport is available at the STLport.org web site.

MPW is available at the MPW web page and on the Apple Developer CD Series.

Known Problems

STLport 3.2.1 doesn't compile correctly with the versions of MrCpp and the Universal Interfaces that are currently available. It is possible that moving to STLport 4.0 would help.

Linking a PPC debug version of a simple MacApp application fails on systems with only 128 MB RAM.
