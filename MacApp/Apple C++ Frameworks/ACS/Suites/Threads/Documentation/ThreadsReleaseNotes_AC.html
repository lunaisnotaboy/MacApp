ACS Threads Suite

 

Threads are a means for improving the responsiveness of your application, and for allowing your application to perform more than one operation at the same time. With ACS Threads framework classes, a developer can add threads to their applications with only a modest effort.

The architecture is a simplified version of the Taligent CommonPoint threads framework, which supported Mach threads in its original implementation. The ACS version supports the Mac OS Thread Manager and MP tasks.

Revised for MacApp Release 14

The threads suite has been reorganized to be simpler, safer and easier to use. It provides better support for working with the Thread Manager and the Multiprocessing Library. Now it is possible to use cooperative threads without pulling in MP support that you don't want. It also is easy to use a mix of cooperative threads and MP tasks.

General Thread Classes

CThread_AC

CThread_AC is the abstract base class for threads. It used to be that application threads were created by subclassing from CThread_AC. Now it is recommended that application threads subclass from CCooperativeThread_AC or CPreemptiveThread_AC. You should subclass from CThread_AC only if you want to implement support for a new kind of thread, like Windows threads.

With the new design, developers don't have to deal with thread context objects. APIs that used to be only in CAbstractThreadContext_AC are now available in CThread_AC:

  • IsAlive
  • IsCurrent
  • Resume
  • PostException
  • ThrowIfHasException
  • Acquire
  • Release
  • IsReferenced
  • fRefCount

The ShutdownRequested method has been made virtual so a thread can override to look at an adopted thread's flag instead of its own.

The CreateThreadContext method has been renamed to Start, because that's what it really does.

The PostException method has been changed to take separate error and message number arguments, so the caller doesn't have to construct a CException_AC object.

The Prepare method has been removed. It didn't really work as advertised and added complexity that most threads don't need. If you need synchronized initialization, create a semaphore, run the thread, and wait on the semaphore. The thread should call whatever prepare code it wants to at the beginning of its Run method, then set the semaphore. However, you should consider doing the preparation in your thread object's constructor, or by calling a method of your thread object before starting the thread.

An abstract Join method has been added so the code that was in CThreadRunner_AC could be moved to the thread.

CThreadHandle_AC

CThreadHandle_AC now references a CThread_AC rather than a CAbstractThreadContext_AC.

Added a copy constructor, assignment operator, accessor operator, dereference operators, boolean operators and comparison operators, and get, reset and release methods. This makes CThreadHandle_AC a fully functional ref-counting pointer class.

CThreadRunner_AC

CThreadRunner_AC descends from CThreadHandle_AC, so it inherits all the ref-counting pointer functionality. The IsSelf, Exists, RequestShutdown, Join and Resume methods have been moved to the thread. Because CThreadRunner_AC is a smart pointer, all you have to do is change "." to "->" in your code:

    runner->RequestShutdown();  // instead of runner.RequestShutdown();

Also because CThreadRunner_AC is a smart pointer, there is no need to create it on the heap. Here is an updated version of the thread example code that takes advantage of the new CThreadRunner_AC design:

class TSimpleThreadView : public TView
{
public:
    // etc.
    void StartThreadExample();
        // Creates a thread and runs it, storing its thread runner in fThread.
	
    void StopThreadExample();
        // Stops fThread by requesting a shutdown and joining the thread (waiting for it to stop).
	
private:
    CThreadRunner_AC fThread; // Runner for the thread that is calling DrawSpirograph.
};

void TSimpleThreadView::StartThreadExample()
{
    if (!fThread)
        fThread = TH_new TSimpleThread(this);
    // etc.
}

void TSimpleThreadView::StopThreadExample()
{
    if (fThread)
    {
        fThread->Join(); // request shutdown and wait
        fThread.reset();
        // etc.
    }
}

As you can see in the example, all that's necessary to start a thread is to assign it to a thread runner. On the other hand, because all of the necessary infrastructure for starting threads has been moved from CThreadRunner_AC into the thread itself, you really don't need to use CThreadRunner_AC if you don't want to. For example, if you want to "fire and forget" a thread, you can do this:

    (TH_new TSimpleThread(this))->Start();

Calling Join as in StopThreadExample is necessary only if you want to stop a thread but keep the around the CThreadRunner_AC. CThreadRunner_AC automatically calls Join for you in its destructor.

Removed ThreadParameters_AC and the DefaultStartRoutine_AC function. Now CMPThread_AC and CThreadMgrThread_AC have their own start routines which are static member functions. ThreadParameters_AC was needed primarily for synchronized preparation, which is better done in other ways.

CThreadNotification_AC

CThreadNotification_AC is a structure that holds three void* parameters. This matches the data that can be transmitted through a CMPQueue_AC or a CThreadQueue_AC. It's used internally in the implementation of CThreadQueue_AC, and it's available as a convenience for use with either kind of queue.

CTime_AC

(No changes.)

This class and its derived classes provide automatic conversion between very small time units.

CTimerTask_AC

CTimerTask_AC is a subclass of the toolbox TMTask structure. It provides an object-oriented API for Time Manager tasks. CTimerTask_AC takes care of the details of initializing the TMTask structure with the appropriate values. It knows how to get the TMTask pointer on PowerPC and 68K, and it sets up the A5 world on 68K.

To create a timer task, subclass from CTimerTask_AC, override the DoTimer method, make an instance and call its Install method. To start the timer, call the Prime method with the timer count in milliseconds. The Disable method leaves the timer running but ensures that the timer proc will not be called. The Enable methods reconnects the timer proc. The destructor automatically removes the timer.

CYielder_AC

CYielder_AC provides an API for smoothing out thread performance. You can call the yielder's YieldIfTime method as often as you want, and it will actually yield only once per tick, or however many ticks you specify. This way your code will never go on too long without yielding, but you can also be sure it won't spend too much time doing thread switching instead of useful work. If you really want the thread to yield no matter what, you can call the YieldNow method.

CYielder_AC is a base class that never yields. CThreadYielder_AC is a subclass that knows how to yield with Thread Manager threads. For obvious reasons, there is no MP yielder.

Cooperative Threads

CCooperativeThread_AC

CCooperativeThread_AC is a CThreadMgrThread_AC. However, this is the one you should subclass from. CCooperativeThread_AC will always map to the best cooperative thread implementation for the target platform, while CThreadMgrThread_AC may not be available on all platforms.

To use CCooperativeThread_AC, create your own subclass and override the Run method. Make a new instance of your subclass and assign it to a CThreadRunner_AC to start it.

CThreadMgrThread_AC

CThreadMgrThread_AC is a subclass of CThread_AC that knows how to run itself as a Thread Manager Thread.

You could subclass from CThreadMgrThread_AC, but it's better to use CCooperativeThread_AC.

CThreadMgrThread_AC defines CMutex, CQueue, CSemaphore, CTempMutex, CTempQueue and CTempSemaphore types similar to those in CMPThread_AC, except they are based on the CThreadMutex_AC, etc.

For compatibility with CMPThread_AC, CThreadMgrThread_AC provides FailIf and ProgramBreak functions that map onto ThrowIfOSErr_AC and ProgramBreak_AC.

CThreadList_AC

CThreadList_AC is an array of ThreadID values. It adds PushBack and PopFront methods so it can be used as a queue. It also has a Contains method that tests whether a ThreadID is in the array.

CThreadWaitList_AC

CThreadWaitList_AC is a list of threads that are waiting for something. It is used internally in the implementation of CThreadMutex_AC, CThreadQueue_AC and CThreadSemaphore_AC.

CThreadWaitList_AC is a CThreadList_AC with the addition of a holder, a deletion flag, and a Wait method. The holder is the ThreadID of the thread to wake up. The Wait method adds the current ThreadID to the end of the queue and stops itself. When it wakes up, it checks if the timeout has expired, the list has been marked as deleted, or if it is now the holder. If none of those conditions are true, it goes back to sleep.

The destructor for CThreadWaitList_AC sets the deleted flag and wakes up all the waiting threads.

To do:
Check if we need to add a call to Yield in the wakeup loop so we can be sure all the waiting threads get out of Wait before the wait list is really destroyed.

CThreadMutex_AC

CThreadMutex_AC provides exactly the same features as CMPMutex_AC, only for Thread Manager threads.

CTempThreadMutex_AC is a CThreadMutex_AC that automatically deletes the mutex in its destructor.

CThreadQueue_AC

CThreadQueue_AC provides exactly the same features as CMPQueue_AC, only for Thread Manager threads.

CTempThreadQueue_AC is a CThreadQueue_AC that automatically deletes the queue in its destructor.

CThreadSemaphore_AC

CThreadSemaphore_AC provides exactly the same features as CMPSemaphore_AC, only for Thread Manager threads.

CTempThreadSemaphore_AC is a CThreadSemaphore_AC that automatically deletes the semaphore in its destructor.

CThreadYielder_AC

CThreadYielder_AC is a subclass of CYielder_AC that knows how to yield for Thread Manager threads. If overrides the YieldIfTime and YieldNow methods. It also adds a YieldIfEvent method that will yield specifically to the application thread if there is an OS event pending. YieldIfTime calls YieldIfEvent so it will yield if there is an event or if it is time.

Preemptive Threads

CMPThread_AC

CMPThread_AC is a subclass of CThread_AC that knows how to run itself as an MP task.

To use CMPThread_AC, create your own subclass and override the Run method. Make a new instance of your subclass and assign it to a CThreadRunner_AC to start it.

If you want MP tasks on PowerPC and don't care about 68K preemptive thread support, you could subclass from CMPThread_AC instead of CPreemptiveThread_AC. However, it still is better to subclass from CPreemptiveThread_AC because that class is about providing a particular kind of functionality, while CMPThread_AC is a class that wraps a particular kind of implementation.

As a convenience, CMPThread_AC defines CMutex, CQueue, CSemaphore, CTempMutex, CTempQueue and CTempSemaphore as types based on the MP implementations: CMPMutex_AC, etc. If you use these types in your code, they will map onto the appropriate synchronization classes for the thread class that you are inheriting from.

CMPThread_AC provides FailIf and ProgramBreak functions that map onto MPFailIfOSStatus_AC and MPProgramBreak_AC.

CPreemptiveThread_AC

On PowerPC, CPreemptiveThread_AC is a CMPThread_AC. On 68K, it's a CThreadMgrThread_AC that it starts as a kPreemptiveThread.

CMPFailure_AC

CMPFailure_AC provides a way for code in an MP task to signal failure.

It does not appear that C++ exceptions work in MP tasks. Instead of calling ThrowIfOSErr_AC, call MPFailIfOSStatus_AC. If the provided status is an error, it will terminate the current task with that error status. Please note that catch blocks and destructors will not be called when the task is terminated. Since C++ exceptions don't work in tasks, the catch blocks and destructors don't get called if you throw either. Destructors still work for cleanup when there aren't any errors, but otherwise you can't rely on C++ exception handling in MP tasks. The best approach is to make sure the code in an MP task will never fail at runtime.

MP tasks now have a task exception mechanism but it is more for task debugging. It does not correspond to the C++ language exception mechanism that can operate at the object and function level. MPFailIfOSStatus_AC may be changed to throw an MP task exception in addition to terminating the task. That will provide more information about the failing task, but it's not possible to catch an MP task exception in the same task that threw it.

If it becomes possible to use C++ exceptions in MP tasks, MPFailIfOSStatus_AC will be changed to throw a C++ exception.

MPFailIfOSStatus_AC can be called from non-preemptive code. If it is safe to throw a C++ exception, it calls ThrowError_AC or DebugThrowError_AC. If it is in an MP task, it calls MPProgramBreak_AC to report the failure, then terminates the task.

CMPFailure_AC provides MPProgramBreak_AC functions for safe debugging from MP tasks. The function is overloaded so you can give either a pascal string or printf style arguments.

CMPMutex_AC

CMPMutex_AC is a simple wrapper on a MPCriticalRegionID.

CTempMPMutex_AC is a CMPMutex_AC that automatically deletes the mutex in its destructor.

CMPQueue_AC

CMPQueue_AC is a simple wrapper on a MPQueueID.

CTempMPQueue_AC is a CMPQueue_AC that automatically deletes the queue in its destructor.

CMPSemaphore_AC

CMPSemaphore_AC is a simple wrapper on a MPSemaphoreID.

CTempMPSemaphore_AC is a CMPSemaphore_AC that automatically deletes the semaphore in its destructor.

Obsolete Classes

CAbstractMonitorLock_AC, CMPMonitorLock_AC, and CThreadMgrMonitorLock_AC are in the process of being replaced by CMPMutex_AC and CThreadMutex_AC.

CWinMonitorLock_AC is currently broken and will be removed. Eventually there should be a CWinMutex_AC to replace it.

CMonitorCondition_AC will be replaced by CMPQueue_AC and CThreadQueue_AC.

CTempSynchronize_AC is the same thing as CWhileSynchronized_AC. It will be removed.

CWhileSynchronized_AC is in the process of being replaced by the CWhileSynchronized member classes nested in CMPMutex_AC and CThreadMutex_AC.

CAbstractThreadContext_AC, CMPThreadContext_AC, and CThreadMgrThreadContext_AC have been merged into the corresponding thread classes.

CWinThreadContext_AC has been removed. Eventually there should be a CWinThread_AC to replace it.

CAbstractThreadSchedule_AC, CMPSchedule_AC, CThreadMgrSchedule_AC and CWinSchedule_AC have been removed. You can choose the kind of threads you want by subclassing from CCooperativeThread_AC or CPreemptiveThread_AC.

CThreadedIdleEngine_AC and CThreadedReactorFactory_AC have been removed. They were used only by the old networking suite. There are better and simpler ways of doing what these classes did. In a threaded application, replace DoIdle methods with threads. In a non-threaded application, use MacApp which can deliver idle time to event handlers without a threaded idle engine.

CYieldThread_AC has been removed. It had two features, both of which are better done in other ways. It managed a queue of requests so that MP tasks could ask it to wake up cooperative threads for them. Since the yield thread was a cooperative thread, it clearly would be easier and just as safe to wake up the cooperative threads directly. The yield thread also called MPYield frequently. Since all the cooperative threads, including the main thread, run in the same MP task, it would be easier and use less time and memory to simply call MPYield in the main event loop.

CYieldThread_AC was originally intended to be a server thread that could make non-MP-safe calls on behalf of MP tasks. That functionality was never implemented. The Multiprocessing Library now has an MPRemoteCall function that does just that. It it turns out that ACS should provide a server thread for use on systems that don't have MPRemoveCall, the server thread will not be called CYieldThread_AC.

Using ACS Threads

ACS Threads requires the ThreadsLib and Multiprocessing API Library extensions. These extensions are a standard part of Mac OS 7.6 and newer. To use ACS Threads in your application, you must set the qWantsThreadManager flag to 1. If you want to additionally use multiprocessor threads, you must set the qWantsMP flag to 1. Finer-grained control over features are controlled using other flags which are explained in CoreSwitches_AC.h.

Cooperative Threads

Cooperative threads are easy and safe to work with and offer very good performance. You should add code to yield every once in a while, but that's usually much easier than restructuring code so it can pick up where it last let off in an idle handler.

Implementing a thread

To implement a thread, subclass CCooperativeThread_AC or CPreemptiveThread_AC, implement your Run method, and call key methods of the CThreadRunner class from within your subclass or from the main application thread. The MacApp SimpleThreads example illustrates how to implement a thread and how to start and stop the thread. This section explains how to implement a thread; starting and stopping a thread is explained in the next section.

A TSimpleThread subclass thread is implemented whose Run method continuously calls a MacApp view to perform drawing of a spirograph shape, until the thread is told to stop by a call to RequestShutdown from the main application thread.

Here is the complete interface for CSimpleThread:

class TSimpleThread : public CCooperativeThread_AC 
{
public:
	TSimpleThread(TSimpleThreadsView* theView = NULL);
		// Constructor
 
	virtual ~TSimpleThread();
		// Destructor
		
	virtual void Run();
		// Represents the entry point for the code to be run in the thread
		// Overriden to provide the code the thread is to execute.
		
private:	
	TSimpleThreadsView* fView;
};
 
class TSimpleThreadView : public TView 
{
	// etc.
public:
	
	void DrawSpirograph(int& iter);
		// Draws a portion of a spirograph.
};
 

The key method being implemented by TSimpleThread is the Run method. The constructor and destructor contain no code in this example

void TSimpleThread::Run()
{
	int iter = 0;
	if (fView != NULL) 
	{
		while (!ShutdownRequested())
		{
			fView->DrawSpirograph(iter);
			Yield();
		}
	}
}

The Run method repeatedly calls DrawSpirograph on the TView subclass (a method implemented in the subclass to perform direct drawing), calls Yield after each call to DrawSpirograph in order to be a responsive and cooperative multitasking thread, and checks ShutdownRequested. The DrawSpirograph method uses an iter parameter to help that class keep track of which iteration it is on when drawing--'iter' and the code in DrawSpirograph are implementation details.

Starting and stopping a thread

To create the thread and start it running, the main application thread must create the thread and a thread runner for it. To stop a thread that runs continuously and that calls !ShutdownRequested, a reference to the thread runner must be stored so that its RequestShutdown method can be called to stop the thread. Here are the methods and member data of TView which implement starting and stopping a thread:

class TSimpleThreadView : public TView 
{
	// etc.
public:
	void StartThreadExample();
		// Creates a thread and runs it, storing its thread runner in fThread.
	
	void StopThreadExample();
		// Stops fThread by requesting a shutdown and joining the thread (waiting for it to stop).
	
private:
	CThreadRunner_AC fThread; // Runner for the thread that is calling DrawSpirograph.
};

To create the thread and start it running, the main application thread uses the following from within the StartThreadExample method:

void TSimpleThreadView::StartThreadExample()
{
    if (!fThread)
        fThread = TH_new TSimpleThread(this);
    // etc.
}

The simple thread is constructed with a reference to the TSimpleThreadView, and handed off to the constructor of a CThreadRunner. The CThreadRunner will start the thread which in turn will cause its Run method to get called. The CThreadRunner is stored as member data so that the thread can be stopped when the view is destructed, or when the main application thread requests that the thread be stopped:

void TSimpleThreadView::StopThreadExample()
{
    if (fThread)
    {
        fThread->Join(); // request shutdown and wait
        fThread.reset();
        // etc.
    }
}

In this example, the thread runner is asked to shut down the executing thread by deleting it. The thread runner's destructor will call Join(), which in turn will call the executing thread's RequestShutdown method, informing the thread to shut down (it will exit its Run method's while loop). The Join method will wait until the thread has stopped running. Join in turn calls YieldTo on the curent thread, so that the thread which has a request to stop gets execution time and is able to exit the while loop of its Run method. Once the thread has exited Run, its CThreadRunner will stop and clean up the thread, and control will return to the main application thread.

Synchronization

Few threads are as straightforward as the one in the SimpleThreads example. The primary issue for threads is managing the access and manipulation of shared data from within multiple threads that may possibly be executing simultaneously as on a multi-processor, or near-simultaneously as in a preemptive multitasking environment. The MacApp FracAppMP example illustrates this issue.

The FracAppMP example implements an engine class which creates more than one thread to compute and render a fractal image. Since each thread may access the member data of the engine class, and since the example implements multi-processor threads (explained in more detail below), more than one thread may be executing code that records the updating of the current location in the fractal and the code that checks if the calculation has completed. In order to guarantee that only one thread is executing while these steps are being made, the CMutex and CWhileSynchronized classes are used.

Since the CMutex can manage the lock state of multiple threads simultaneously, the FracApp engine implements an instance of CMutex as member data in the engine class:

class CFracAppEngine
{
// etc.
public:
	typedef TFracThread::CTempMutex		CTempMutex;
	typedef TFracThread::CWhileSynchronized	CWhileSynchronized;

	virtual bool CalcCity();
	// Calculates a little bit of the fractal
 
protected:
	CPoint_AC fCurrentLocation; // holds current positon of the "pen".
	CRect_AC fCalcRect;         // rectangle surrounding the window it was built for
	CTempMutex fLock;           // Concurrent access control for fields.
};

The CalcCity method uses the mutex when it reaches crticial code for updating the current location:

bool CFracAppEngine::CalcCity()
{
	// etc.
 
	// Calculate the fractal as we go.  Do next pixel here, based on the state saved
	// in fCurrentLocation. When done, those variables are updated to go to the next
	// location to do.
	bool isFinished = false;		// Assume document is not done.
	CRect_AC tempRect = fCalcRect;
	{
		CWhileSynchronized entry(fLock);
		tempRect.top = fCurrentLocation.v;
		++fCurrentLocation.v;			// Up the counter of next row to do.
	}
 
 
	// etc.
	return isFinished;
}

In this example, there is an access and update of the fCurrentLocation data member. This code above is basically saying "I am now going to work on the current uncalculated part of the fractal, any other thread should work on the next part." If more than one thread is executing this code simultaneously as may happen on a multiprocessor, there is the possibility that more than one thread will think they can work on the same part of the fractal, and part of the fractal may be skipped because the threads will increment the location past an uncomputed part before any thread has had a chance to work on it.

To avoid this situation, the CMutex instance of the CFracAppEngine is handed to a stack-based CWhileSynchronized object, whose constructor will call the Lock method of the monitor lock, and whose destructor will call the Unlock method. The thread which first becomes acquired gets to continue running, and any other threads which attempt to become acquired in the same section of code are suspended in a queue until the release method is called on the monitor lock by the thread that is executing. The brackets around CWhileSynchronized, the location access, and the location update are used to ensure that the destructor is called immediately after the update has completed, so that other threads that may have become suspended can continue running with a minimum interruption.

Preemptive and multiprocessor threads

Multiprocessor tasks offer signficant performance improvements through simultaneous processing of tasks on systems that have multiple processors. Multiple MP tasks on the same processor are time sliced, so an MP task never needs to call yield. MP tasks in the Classic Mac OS are robust and efficient. However, most of the toolbox managers such as QuickDraw are not safe to call from an MP task. Even runtime features such as C++ exceptions should not be used in an MP task. Operating system compatibility with MP will continue to improve, but for now MP tasks should be used mainly for computation.

The initial release of ACS Threads can be made multi-processor (MP) aware by setting the qWantsMP switch to 1, but your threads will not be automatically MP-savvy, nor will they be automatically preemptive. This behavior is by design, in part. preemptive and MP threads support require additional responsibilities in your threaded code that you may not choose to to accept initially. Your application code may also choose to implement a combination of cooperative and preemptive and MP threads.

To implement a preemptive or MP thread, subclass from CPreemptiveThread_AC instead of CCooperativeThread_AC.

FracAppMP provides an example for a preemptive thread:

class TFracThread : public CPreemptiveThread_AC
{
public:
	TFracThread(CFracAppEngine* theEngine = NULL);
		// primary constructor

	virtual ~TFracThread();
		// Destructor

private:
	TFracThread& operator=(const TFracThread& sourceThreadProgram);
		// Assignment operator -- don't allow copying

public:
	virtual void Run();
		// Represents the entry point for the code to be run in the thread
		// Override this method to provide the code the thread is to execute.

private:
	CFracAppEngine* fEngine;
};
